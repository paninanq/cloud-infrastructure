# Лабораторная работа №3 — «Безопасность облачной инфраструктуры»

## 1. Цель работы

Закрепить на практике знания, полученные в лекции №3 «Безопасность облачной инфраструктуры»:

- применить модель Shared Responsibility (разделение ответственности между провайдером и клиентом);
- спроектировать управление доступом (IAM): роли, политики, сервисные аккаунты, принцип минимальных привилегий;
- организовать безопасное хранение секретов (Vault / AWS Secrets Manager) с ротацией;
- обеспечить шифрование данных in-transit (TLS) и at-rest (диски, S3, БД) через KMS;
- спроектировать многоуровневую сетевую защиту: Security Groups, Network ACL, WAF;
- избежать типичных ошибок, перечисленных в лекции, и задокументировать результат.

На выходе вы получаете проект решения по безопасности облачной среды для выбранного сервиса и отчёт. Разворачивать или изменять облачную инфраструктуру в этой работе не требуется.

## 3. Исходные данные (условие задачи)

Вы — DevOps-инженер выбранного проекта из лабораторной работы №1 (например, интернет-магазина «Книжный мир»). Укажите его название и специфику. После проектирования сетевой архитектуры в лабораторных №1 и №2 заказчик поручает вам описать безопасность облачной среды. Сеть, подсети, CIDR, IGW/NAT и балансировщики берутся из предыдущих работ без изменений.

В заданиях используется терминология и формат AWS как общий учебный пример. При проектировании для Яндекс Облака, VK Cloud или Cloud.ru сопоставляйте IAM, объектные политики, KMS и сетевые фильтры с эквивалентами выбранного провайдера.

Для проектирования вам доступны следующие компоненты инфраструктуры:

| Компонент | Назначение | Требование к безопасности |
|---|---|---|
| Веб-фронтенд | Публичный сайт магазина | HTTPS (TLS 1.2/1.3), защита от атак L7 (SQLi, XSS) |
| API-бэкенд | Логика заказов, каталог | Доступ только из внутренней сети, роли IAM с мин. правами |
| База данных | Хранение каталога и заказов | Недоступна из интернета, шифрование at-rest, секрет в хранилище |
| Служебные сервисы | Бэкапы, телеметрия, CI/CD | Сервисный аккаунт с ролями, ротация ключей, секреты в менеджере |
| S3-бакет | Хранение статики и артефактов | Шифрование объектов, точечная политика доступа |

**Требования заказчика к безопасности:**

- Доступ к сервисам — через роли IAM и сервисные аккаунты, без постоянного root-аккаунта в production.
- Все секреты (пароли БД, ключи, токены) хранятся только в менеджере секретов, не в коде.
- Все данные шифруются in-transit (TLS) и at-rest (диски, S3, БД, бэкапы). Используйте KMS для управления ключами там, где выбранный сервис это поддерживает; для управляемых сервисов зафиксируйте документированный механизм шифрования провайдера.
- Трафик фильтруется на трёх уровнях: WAF, Network ACL и Security Group; фактический порядок зависит от размещения WAF и ресурсов в сети.
- Ведётся аудит: логирование действий в IAM, доступа к секретам, использования ключей.
